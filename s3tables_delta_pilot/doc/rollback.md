# Product Requirement: S3 Table Snapshot & Rollback

## Objective

Protect the master dataset from incorrect monthly uploads by using **Amazon S3 Tables / Apache Iceberg snapshots**.

Every successful monthly data update must create an Iceberg snapshot so an administrator can restore the master table to its previous known-good state.

## Functional Requirements

### 1. Capture Snapshot Before Upload

Before modifying the master S3 Table:

* Retrieve the table's current Iceberg snapshot ID.
* Store this as the `previous_snapshot_id`.
* Record:

  * snapshot ID
  * upload ID
  * filename
  * reporting month
  * uploader
  * timestamp
  * row count before upload
  * status

Example:

```text
Upload ID: UPLOAD-2026-08-001
Month: 2026-08
Previous Snapshot: 847293847293
Uploaded File: august_2026.csv
Status: PROCESSING
```

### 2. Perform Monthly Upload

Process:

```text
User uploads file
       ↓
Validate file
       ↓
Get current snapshot ID
       ↓
Save snapshot ID to upload history
       ↓
INSERT / MERGE data into master Iceberg table
       ↓
Iceberg creates new snapshot
       ↓
Record new snapshot ID
       ↓
Mark upload SUCCESS
```

The master table must only be modified after validation succeeds.

### 3. Upload History

Create an audit/history table containing at minimum:

```text
upload_id
reporting_month
filename
uploaded_by
uploaded_at
previous_snapshot_id
new_snapshot_id
rows_before
rows_uploaded
rows_after
status
rollback_at
rollback_by
```

Example UI:

```text
Monthly Upload History

Month     File              Rows      Status
------------------------------------------------
2026-08   august.csv        12,430    SUCCESS
2026-07   july.csv          11,982    SUCCESS
2026-06   june.csv          12,105    SUCCESS
```

### 4. Rollback Function

Admin users must have a:

**Rollback Upload**

function.

When selected:

```text
Admin selects upload
       ↓
System displays snapshot information
       ↓
Admin confirms rollback
       ↓
Restore table to previous_snapshot_id
       ↓
Verify restoration
       ↓
Record rollback in audit history
```

The UI must clearly warn:

> Rolling back will restore the master table to its state immediately before this upload.

Rollback must only be available to authorised admin users.

### 5. Verification

After rollback, automatically verify:

* current table snapshot
* expected row count
* rollback operation status

Never mark the rollback successful until the table state has been verified.

### 6. Snapshot Retention

Configure S3 Tables snapshot management so snapshots remain available long enough for operational recovery.

Recommended initial requirement:

```text
Minimum snapshots retained: 12
Maximum snapshot age: 365 days
```

This provides approximately one year of monthly recovery points, although additional snapshots may be generated by other table operations.

Do NOT rely on the S3 Tables defaults because old snapshots can be automatically expired.

### 7. Failure Handling

If an upload fails:

* Do not attempt to treat the partially processed upload as successful.
* Mark upload status `FAILED`.
* Preserve the previous snapshot ID.
* Verify that the master table remains in a consistent state.

If rollback fails:

```text
status = ROLLBACK_FAILED
```

and alert/log the error for administrator investigation.

### 8. Permissions

Normal users:

```text
Upload
View upload status
```

Admin users:

```text
View upload history
View snapshot IDs
Initiate rollback
Confirm rollback
View rollback history
```

The application IAM role should follow least-privilege access.

## Key Design Principle

Never implement recovery as manually deleting the rows from the bad monthly upload.

Use the Iceberg table snapshot as the recovery point:

```text
Snapshot A
Master data before August upload
        ↓
August upload
        ↓
Snapshot B
Master data after August upload

Bad upload detected
        ↓
ROLLBACK
        ↓
Snapshot A restored
```

This makes recovery deterministic and auditable.
