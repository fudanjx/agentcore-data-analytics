## Purpose and boundaries

The uploader accepts healthcare source files, profiles them in isolated
Fargate workers, sanitises them before staging, and creates, appends, or rolls
back S3 Tables/Iceberg data. S3 is the durable application store. SQS provides
durable FIFO delivery. No DynamoDB, EFS, Lambda, or EKS is required.

- The API/UI accepts files, authenticates and authorises users, owns browser
  session state, and exposes durable status. It does not transform datasets.
- A leased worker handles profile, repeated key-impact analysis, final
  sanitisation, and preparation for one session using a local encrypted cache.
- One permanent dispatcher is the sole component allowed to start and monitor
  Glue mutations.
- Glue performs the actual S3 Tables/Iceberg mutation and writes audit/QC
  records. It has no queue or table-lock release arguments.

## Durable state and migration

New records are written only beneath `s3-uploader/` in the existing versioned,
encrypted landing bucket. The narrow `S3JobStore` adapter reads the legacy
`s3-uploader-v2/` prefix only if no neutral record exists. Historical objects
are never rewritten. An in-flight historical browser session is copied into
the neutral prefix before its first V3 state update; source object version and
checksum remain unchanged.

| Data | Neutral location |
| --- | --- |
| Raw upload objects | `s3-uploader/uploads/<session>/raw/` |
| Browser session | `s3-uploader/compat-sessions/<session>/session.json` |
| Worker lease | `s3-uploader/worker-leases/<lease>/lease.json` |
| Job request/status/events | `s3-uploader/jobs/<job>/` |
| Mutation command/request mapping | `s3-uploader/mutations/` and `mutation-requests/` |
| Prepared Parquet/manifest and QC | `s3-uploader/jobs/<job>/prepared/`, `s3-uploader/qc/` |
| Table contract/history | `ah-data-analytics/temp_s3_update/web_ingest/` |

## Identity and administration

The pilot UI emulates `local-admin`, `local-editor`, and `local-unassigned`
through a backend-controlled header. A production identity provider must map
users at this boundary; a browser must never submit a role, bucket scope, or
rollback entitlement.

- Administrators discover every customer S3 Tables bucket in the account and
  can create table buckets/namespaces and delete uploader-managed tables.
- Editors are restricted to their configured bucket assignments and may use
  permitted history/rollback/skill operations.
- Unassigned users are denied.

## Skill bundles

Administrators and assigned editors can list, upload, download, and delete
skill files through the non-versioned `/api/skills/files` API. The API stores a
bundle for each selected S3 Tables bucket at
`s3://agentcore-harness-dev/skills/<table-bucket-name>/`; an uploaded root
`SKILL.md` has its frontmatter `name` aligned to that table-bucket name. The
API task role alone has prefix-scoped `ListBucket`, `GetObject`, `PutObject`,
and `DeleteObject` permissions for this store. Skill configuration uses only
`S3_UPLOADER_SKILL_BUNDLE_BUCKET` and `S3_UPLOADER_SKILL_BUNDLE_PREFIX`; the
retired `PILOT_SKILL_BUNDLE_*` variables are not read.

## Worker lifecycle and routing

At file selection the API computes the routing score from extension and byte
size. Browser MIME type is ignored. `.parquet.gzip` is matched before shorter
suffixes, matching is case insensitive, and missing/invalid sizes fail closed.

| Format | Base-worker allowance |
| --- | ---: |
| Parquet / Parquet GZIP | 128 MiB |
| CSV / TSV | 64 MiB |
| XLS / XLSX | 32 MiB |

`score <= 1.0` selects a 4 vCPU / 16 GiB worker; a higher score selects 8
vCPU / 32 GiB. Same-tier selection changes reuse an idle lease and task. A
tier change cancels the idle lease and starts one replacement because Fargate
tasks cannot resize. A live preparation or post-acceptance session is never
rebound.

The worker waits ten minutes for an upload and 30 idle minutes for key or
confirmation input. It heartbeats S3 every ten seconds and exits after final
preparation/Glue submission, cancellation, or expiry. If a base worker reaches
the documented memory/storage/OOM guards before Glue submission, only an
owner-triggered large-worker retry is available. There is no automatic
promotion and no concurrent base/large task for the same lease.

**Cancel & Start Over** is available only before ingestion is accepted. It
cancels the lease cooperatively, aborts exact-version multipart work, deletes
new temporary state/cache, resets browser inputs, and does not alter any
accepted job or Glue mutation.

## File, schema, privacy, and de-duplication rules

Supported files are Parquet, Parquet GZIP, CSV, TSV, XLSX, and XLS. Multi-file
upload requires matching normalised column-name sets; order does not matter.
Types may differ: the worker uses a safe common type, including `STRING` for
conflicts. An append requires at least a 50% normalised match to the immutable
table contract; unmatched inputs are ignored and missing target columns become
typed `NULL`.

When a reviewed contract requires `BIGINT` or `DOUBLE`, the worker trims
whitespace around source string values before conversion. Blank strings become
`NULL`; valid padded numbers are retained; any other non-empty value still
fails preparation with its column name and the count that would be discarded.

Sanitisation occurs only in the worker before temporary S3 staging. Names,
DOBs, contact data, and addresses are removed; patient/case/account
identifiers are encrypted; age is banded; postal codes retain two digits;
manual selections and detected NRIC-shaped values are encrypted. Review may
show up to five short non-empty examples only when a candidate is not
protected. Protected examples and quality counts are always masked and are
never stored in manifests, history, or Glue arguments.

The first acknowledged key becomes the table's immutable key universe. Later
uploads derive the active key from the locked columns that are present in that
source. If none occur, the append continues without deduplication and informs
the user. The lock is not changed and a selector is never shown once a key is
configured. Raw values, not sanitised values, decide same-key duplicates and
conflicts, preserving cross-era records that happen to share an identifier
subset.

## Mutation ordering and recovery

One FIFO mutation queue carries immutable command IDs. Its message group is
the table identity hash, so the order of one table is preserved while different
tables can use available Glue capacity concurrently. The single dispatcher
retains a receipt until it has observed terminal Glue state, persisted status,
released its conditional S3 table lock, and deleted the receipt.

- Same-table work is queued, never rejected as busy.
- Different tables may run concurrently up to `GlueJob.MaxConcurrentRuns`.
- Glue capacity errors leave the durable command in `READY_FOR_MUTATION` for
  retry; Glue queuing is also enabled.
- Dispatcher restart reconstructs active state from S3 locks/statuses.
- Duplicate deliveries are idempotent through immutable command records,
  owner/request mapping, status transitions, and Glue run reconciliation.

## History and rollback

Glue writes a value-free audit projection and Iceberg audit record per
mutation. Table cards use Iceberg snapshot metadata for row counts and render
created/modified times in `Asia/Singapore`.

Only the latest successful uploader-managed update with a recorded preceding
snapshot is rollback eligible. Rollback needs explicit confirmation, follows
the same FIFO group, reloads Iceberg metadata after the operation, verifies the
restored snapshot and row count, and records success/failure in history. Do
not retry an ambiguous rollback automatically.

## Operational checks

1. API `/healthz` is healthy and its ECS service has one desired/running task.
2. Dispatcher service has one desired/running task; it is not an EventBridge
   target and directly long-polls the mutation queue.
3. Base/large queues feed EventBridge Pipes; mutation queue does not.
4. All DLQ visible-message metrics are zero.
5. CloudWatch shows no stale table locks or stuck `STARTING_GLUE` status.
6. Use S3 status and Glue run ID for progress; ECS task state alone is not a
   user outcome.
