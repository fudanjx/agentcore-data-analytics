## Purpose and fixed boundaries

V3 preserves the V1 uploader's data rules and frontend experience while moving
large-file work off the shared EC2 host. The API/UI service is a small,
continuously running Fargate task. A one-shot, isolated worker handles the data
work. S3 is the only durable application store; DynamoDB, EFS, EKS and Lambda
are intentionally not used.

- The API authenticates, receives uploads, starts work, and serves durable
  status. It never profiles, sanitises, deduplicates, or transforms data.
- One leased Fargate task owns one session across profile, key analysis, and
  final preparation. It starts Glue then exits.
- S3 stores raw versions, sessions, leases, job request/status/event records,
  manifests, prepared Parquet, table contracts, QC reports and history.
- The dedicated Glue job s3-uploader-v3-ingest performs S3 Tables/Iceberg
  create, append, audit and rollback mutations. V1's Glue deployment must not
  overwrite V3's job/script.
- The ordering is mandatory: raw key selection first, sanitisation second,
  type projection/staging third, Glue last. Deduplicating sanitised output is
  incorrect because transformed identifiers can collapse raw-distinct rows.

## V3 worker lease design

### Deterministic routing

On file selection, the API—not the browser—calculates:

~~~text
routing score = sum(file size in bytes / format allowance)
score <= 1.0 => BASE; score > 1.0 => LARGE
~~~

| Case-insensitive extension | Base allowance |
| --- | ---: |
| .parquet, .parquet.gzip | 128 MiB |
| .csv, .tsv | 64 MiB |
| .xls, .xlsx | 32 MiB |

.parquet.gzip is matched before shorter suffixes. Browser MIME type is not
trusted. Unsupported extension, absent name, zero/negative size, or absent
size is rejected before dispatch. A 100 MiB Parquet is base; 300 MiB Parquet
is large; two 64 MiB Parquet files route to base; 40 MiB XLSX routes large.

### Selection changes and task reuse

The first non-empty selection launches one lease through the route-specific
FIFO queue and EventBridge Pipe. Before the multipart review upload attaches a
session:

- Same deterministic size: update the existing lease's files/score/reason and
  reuse its task. No extra task is launched.
- Different deterministic size: Fargate cannot resize. Mark the old idle lease
  CANCELLED and start exactly one replacement at the new fixed size.
- Empty selection: cancel the unattached lease.
- Attached source objects are immutable. A rejected/profile-only attached
  session may detach from its existing task and yield that compatible task to a
  corrected selection; the abandoned session/source object is never mutated.

An unattached lease expires after 10 minutes. An attached worker can wait 30
idle minutes for key selection/confirmation. It checks lease cancellation and
expiry from S3 every two seconds, and writes a heartbeat every ten seconds
while a child phase runs. A task that was already starting when cancelled exits
safely.

### One worker across the session

One fixed-size worker downloads immutable object versions to encrypted
temporary storage and reuses that cache for:

1. initial profile and sanitisation review;
2. any number of user-requested key-impact analyses;
3. final raw-key selection, sanitisation, validation and prepared Parquet;
4. Glue submission.

Each action runs in a child process. The parent monitors memory, disk, status,
expiry and cancellation. Local cache loss is recoverable: S3 object version
IDs/checksums remain authoritative and a later worker can download again.
Temporary cache is deleted at terminal state.

### Manual large retry only

There is no automatic promotion. A base worker stops before Glue submission and
records RESOURCE_LIMIT_EXCEEDED when RSS reaches 12 GiB, temporary storage
reaches 70%, Python raises MemoryError, Arrow/Polars allocation fails, or an
equivalent resource termination is detected. Earlier profile/key output stays
durable in S3.

Only then may the UI offer Retry using large worker. Retry uses the same
immutable sources, restores completed work, and restarts only the interrupted
phase. It cannot retry after a possibly-started Glue submission; the old base
and replacement large worker never run concurrently.

## File, schema and multi-file contract

Supported formats are Parquet, Parquet GZIP, CSV, TSV, XLSX and XLS. A session
can contain multiple files. All selected files must have the same normalised
set of column names. Order does not matter. Normalisation lowercases and
converts spaces, slashes, parentheses and hyphens to collapsed underscores.

Different inferred Arrow types are allowed. For a new table, a column whose
type differs across files is explicitly stored as STRING in the reviewed
target contract and listed in multi_file_schema.type_conflicts_stored_as_string.
For append, the immutable target-table contract determines conversion; a later
source does not change a live table's type contract. Multi-file rejection is
limited to missing/additional normalised columns or separate append contract
validation failure.

Create uses the reviewed target contract. Append requires an uploader contract
and at least 50% normalised source-to-initial-table schema match per file. The
worker projects to exact field order/types and supplies null contract columns
where appropriate. Tables without an uploader contract are browse-only and are
not safe V3 append/rollback targets.

## Sanitisation, encryption and Glue-compatible data types

Sanitisation is mandatory, worker-only, and occurs before temporary staging.
Review records are value-free.

| Data category | V3 action |
| --- | --- |
| Patient name, DOB, phone/contact, home address/street/building fragments | Drop column |
| HRN/MRN, CSN, patient/case/account/subvention identifiers | AES encrypt; store string |
| Postal/ZIP | Keep two digits; store string |
| AGE | Band age; store string |
| Detected NRIC in eligible string column | AES encrypt; store string |
| User-selected manual encryption candidate | AES encrypt; store string |

NRIC detection uses a deterministic safe sample of up to five populated values
and flags at least three matching NRIC-shaped values; it is a heuristic, not a
checksum validation service. Manual selection is allowed only for candidates
returned by the worker review.

Target types are STRING, BIGINT, DOUBLE, BOOLEAN, DATE, and TIMESTAMP.
Timestamp output is always microsecond precision because Glue rejects Parquet
TIMESTAMP(NANOS). Time-only Arrow values are strings because Glue/Spark rejects
Parquet TIME(MICROS). A temporal conversion that would discard populated input
values fails instead of silently nulling them.

## De-duplication contract

The first user-acknowledged key is persisted in the table contract and never
changes. After that, the UI must hide the key selector. For every append, V3
derives the active key from the locked columns common to every incoming file.

~~~text
locked table key = A + B + C + D + F
incoming columns = C + D + F
active key        = C + D + F
~~~

If no locked column is present, the append proceeds without deduplication and
the user is informed. It is not rejected. The locked key remains unchanged.
This intentionally does not cross-match records across eras: an old
A+B+C+D+F row and a new B+C+D row are not automatically the same record.

For a table with no stored key, the selector stays visible. A key requires
impact analysis plus an unexpired acknowledgement token. The first accepted
key is then saved prospectively; existing rows are never rewritten.

The exact V1 raw semantics apply to the current incoming batch:

- exact same-key, exact same-row duplicates retain one row;
- same-key, different-row conflict groups skip every row in that group;
- raw-distinct values remain distinct even if later sanitisation makes them
  look equal.

Impact analysis returns incoming rows, unique keys, exact duplicate rows,
conflicting key groups/rows, expected retained rows and expected skipped rows.
Its acknowledgement token expires after 30 minutes.

## Final preparation and Glue mutation contract

For an acknowledged ingestion, the worker loads immutable source versions,
selects retained raw rows if an active key exists, sanitises those rows in
bounded batches, projects every output file to the reviewed ordered contract,
and writes Glue-safe Parquet plus a manifest. The manifest identifies all
prepared files, schema, sources, row/deduplication metrics, sanitisation
metadata and immutable upload context.

Glue validates the manifest, creates or appends the target Iceberg table, and
records the table snapshot before and after mutation. It writes a QC report and
audits success or failure. Row-count reconciliation is intentional protection:
a mismatch is a failed outcome requiring investigation, not a reason to repeat
an unbounded append. API session polling mirrors durable job state and then
Glue state so the browser reports the terminal outcome rather than remaining
queued.

## Tables, history and rollback

Administrators discover all S3 Table buckets in the account, list namespaces
and tables, create namespaces, view cards, delete uploader-managed tables, and
use uploader history/rollback. Table cards show Iceberg snapshot total-records
without scanning data; the UI formats their ISO timestamps in Singapore time.
The reserved uploader_upload_history table is never a master destination and
cannot be deleted or rolled back through the UI.

Every Glue mutation writes both an append-only Iceberg audit row and a
value-free encrypted JSON projection at:

~~~text
s3://ah-data-analytics/temp_s3_update/web_ingest/upload_history/<scope>/<table>/
~~~

Records include upload ID, original actor/time, filenames, reporting month,
snapshot IDs, rows before/uploaded/after, duplicate/conflict/overlap metrics,
sanitisation choices, timings, status and error details.

Only the latest successful uploader-managed update may be rolled back, only
with explicit confirmation, and only when it has a previous snapshot. An
initial create has no previous snapshot and cannot use this rollback. Glue
rolls the table to the recorded snapshot, reloads Iceberg metadata directly to
avoid a stale Spark cache, verifies expected row count, and writes QC/audit
state. A verification mismatch needs investigation; do not blindly retry.

investigation and history/rollback support.

## Status, failure and operating guidance

Lease states: STARTING, AWAITING_UPLOAD, PROFILING, AWAITING_KEY,
ANALYSING_KEY, AWAITING_CONFIRMATION, PREPARING, COMPLETED,
RESOURCE_LIMIT_EXCEEDED, FAILED, EXPIRED, CANCELLED.

The UI session phases include RECEIVED, PROFILING, READY_FOR_REVIEW,
KEY_ANALYSING, READY_FOR_ACKNOWLEDGEMENT, QUEUED, STARTING_GLUE,
GLUE_RUNNING, SUCCEEDED, and FAILED. Durable job status mirrors worker and
Glue phases. The API calls Glue GetJobRun while RUNNING_GLUE, so API
replacement/page refresh cannot leave a UI permanently queued.

For an issue, inspect durable lease/session/job records first, then ECS stopped
task reason/worker CloudWatch log, then Glue/QC/manifest. A stopped worker is
normally expected after completion, cancellation, or expiry. Never use the
legacy lambda_s3tables_loader/handler.py for this workflow because it uses
overwrite semantics. Do not retry ambiguous create/append operations until the
target table, Iceberg snapshot, manifest, QC report and history are inspected.

## Production concurrency design

### Upload isolation

Each upload has its own authenticated owner, session ID, lease ID, job/request
ID, version-pinned source objects, S3 prefix, status records, manifest, QC and
history reference. Workers only receive their lease/job ID and reconstruct
sources from that durable record. Concurrent users can profile, run impact
analysis and prepare different uploads without shared local state or data
mixing.

### Compare-and-swap durable state

Lease and compatible-session JSON records are no longer blindly overwritten.
They are read with the current S3 ETag and changed with `IfMatch`; a failed
precondition reloads, merges the intended fields and retries a bounded number
of times. Every successful mutation adds one to `state_version`.

This fixes the material 2026-09-10 incident in which a worker had read an idle
lease, the API then bound an uploaded session, and the worker's stale heartbeat
wrote `session_id: null` back to S3. The task eventually expired normally,
while the UI stayed in `RECEIVED`. A heartbeat can now change only heartbeat,
message/state and its explicit phase fields; it preserves newer session ID,
expiry, cancellation, retry and terminal fields. If a lease expires with a
live pre-Glue session, the worker writes `WORKER_LEASE_EXPIRED` as a terminal
session error, so the browser does not poll indefinitely.

### Per-table mutation lock

The key rule is parallel preparation, serial table mutation. Immediately
before calling Glue, a worker acquires an S3 conditional lock at:

~~~text
s3-uploader-v2/table-locks/<sha256(table_bucket_arn, namespace, table)>.json
~~~

The lock payload contains only owner/request/session IDs, actor, operation,
phase, acquisition time and expiry; it never contains patient data. It uses
`IfNoneMatch: *` for first acquisition and ETag matching for renewal, release
and expired-lock takeover. The worker passes lock bucket/key/ETag to Glue. The
V3 Glue script releases the lock in `finally` after a terminal ingestion or
rollback outcome. If Glue start itself fails, the caller releases the lock.

Rollback uses the same lock, preventing it from racing an append/create.
Different table identities map to different lock keys and remain concurrent.
The current interaction is fail-and-retry, rather than holding an expensive
Fargate task idle: a second same-table mutation gets a clear table-busy error
and must be retried after the existing Glue run completes. Future automatic
queueing may be added, but it must retain this lock as the final writer guard.

### IAM boundary for locking

The Glue execution role's landing-artifacts policy retains read/write access to
the landing bucket and adds `s3:DeleteObject` only for
`s3-uploader-v2/table-locks/*`. API/worker task roles have only the landing
S3 actions required to acquire/release on their paths; no broad account
administrator policy was added. Keep this restriction in future IAM changes.

## Resolved defects and behavioural changes

| Area | Fault observed | V3 resolution / invariant |
| --- | --- | --- |
| Shared EC2 | Large Parquet upload exhausted host memory and affected unrelated services | Large parsing/sanitisation runs only in disposable Fargate workers; small API/UI stays isolated. |
| Routing/cost | File edits could create needless same-size Fargate tasks | Reuse compatible lease/task; replace only if deterministic base/large size changes. |
| UI status | Worker/task failure could strand UI in QUEUED/RECEIVED | Durable terminal session/job states and Glue polling drive UI recovery. |
| Lease state | Stale heartbeat could erase API bind | ETag compare-and-swap plus `state_version`. |
| Multi-file uploads | Incompatible inferred types caused unnecessary rejection | Require matching normalised column names; type drift is represented/cast as STRING where required. |

| Key contract | Browser re-requested/chose key after table key was fixed | First acknowledged table key stays immutable; derive only available subset per incoming file set; no available locked columns means no deduplication, not failure. |

| Same table concurrency | Append and rollback could overlap | Conditional table mutation lock spans Glue execution. |

## 2026-09-11 corrective release: retained-row and same-table FIFO handling

The release tagged `20260911-table-fifo-amd64-1` corrected three production
failure modes without changing V1 sanitisation, schema, key-selection, or Glue
append semantics:

1. A multi-file keyed upload can legitimately retain zero rows from one source
   file when every row is a V1 raw-key conflict. The worker now skips only that
   prepared artifact; it still rejects a submission when no rows remain across
   all sources.
2. A browser identity switch cannot attach an editor's selected-file lease to
   an administrator session. The UI clears the owner-scoped lease and the API
   defensively replaces a foreign stale lease with a new lease for the active
   identity.
3. Same-table mutations no longer fail when a prior uploader is in Glue. The
   API writes an ordered S3 queue record per destination table at ingestion
   submission. Workers prepare independently, then wait at the queue head;
   the head acquires the existing table lock and starts Glue. Glue releases
   both lock and queue record in its terminal `finally` block. Different tables
   still process concurrently.

The queue is durable under
`s3-uploader-v2/table-queues/<destination-hash>/`; it contains operational
metadata only. A pending entry expires after 90 minutes and a Glue-running
entry after 120 minutes, providing bounded recovery if a worker is terminated
before it can clean up. The worker IAM role lists only the necessary durable
job, compatibility-session, lease, lock, and queue prefixes. The Glue role has
delete permission only for the lock and queue prefixes in the landing bucket.

The first deployment candidate was ARM64 and ECS correctly rejected it because
this service uses Linux AMD64. It was cancelled before user traffic changed,
then redeployed from explicitly verified AMD64 images. Always build release
images with `docker buildx build --platform linux/amd64` and verify the image
architecture before a CloudFormation update.
